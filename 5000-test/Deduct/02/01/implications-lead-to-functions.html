Next in hour journey into Types as a solution to high-order logic problems we look to consider IMPLICATION ((AB)) also denoted (AB)). This would be a good place to review two concepts: Substitution and Implication. As a quick essential recap

  • A “variable” is a symbol or word designated by context to as a placeholder for a future substitution. In mathematics the context may be implicit with letters like (x) being known as variables owing to years of practice. Meanwhile in programs variables usually much more obvious to spot as they generally require specific syntax. For example the terms in parenthesis such as def doSomehting(time) or the term following a keyword like for in a loop for i in 1:10 .
  • A “substitution” of a variable is to literally remove the symbols of the variable an put in its place the assigned value. There is a catch. You need to avoid trapping variables. When in doubt, rename the variable first, then substitute.
  • Implication has many ways to be introduced but we all agree the invariant property of implication is how we use it, its “elimination rule” also know by the Greek name “Modus Ponens (Mode that Affirms)”

Which implications lead to function types?

We have been careful to acknowledge that logic changes when we change between such modes as “Theory”, “Computation” and “Practice”. With implication we accomplished this by featuring numerous choices to introduce implication along with surrounding context rules like Contraction/Thinning. So when it comes to converting implication to a data type such as a “function” we might need to clarify precisely which type of logic we aim to convert.

Functions with Resource Counting.

If we entertain some of the more nuanced forms of implication such as those that arise with resources we can be forced to express in our notation not that (P) is valid but that a specified number of (P) certificates exist.

(Introduction of Linear Implication)

Recall that (n) is number that counts how many copies of (P) . We can see even in the notation that our new translation will need to keep track of how many times (P) has been validated, that is, how many certificates we have the this. Think for example of the question “Is there a free Compute Thread?” The answer may be YES the first time we ask, and the second, and the third but eventually we consume all the resources and may get a no. That does not take away the validity of our first questions.

Remark. The term “linear implication” comes from Girard who invented this along with the entire field of Linear Logic. If you take a course on “linear algebra” you can learn the mathematical semantics that go with these syntax rules.

In this context the translation from implication to function must keep track of that count. This can be done in a number of ways. Linear logic is one such tool as expressed in programming languages like Idris.

ascii2utf(1 s:Stream):Stream ...

Notice the addition of the number 1 before the input “s”. This tells the computer to use that resource exactly once. That helps the computer know that the stream exists only once can cannot calling it again wont be possible. If the values are needed more than once than the program will be forced to copy it in some way.

Meanwhile if we encountered the following function

json2csv(10 s:BufferedStream):Stream ...

it would be signaling that our program might resume the data in the stream up to 10 times. This would give the program greater options for complex data type conversions (such as parsing JSON—a highly structured format) into CSV—a low-complexity format). By building in a buffer of 10 reuses we can also predict the performance and memory use more accurately.

* Quick Check

You need to ensure a password once entered is used only once. Which type of function I offers this guarantee. - private void login( Password pw) { ... } *

While the function is “private” this only prevents the wrong people calling it, but it does not force the programmers from using the password as many times as they like. Your contract is thus only enforced through code reviews and not through logic. - login(1 pw:Password) : LoginMonad *

Correct: In the syntax of linear logic as demonstrated above, the addition of 1 before the variable limits the use of pw to exactly one use. Be careful, this does not guarantee that the maker of login uses the password properly. They could still use their one-time use to email your password to all your friends. Security is not a one-place fix but instead a tip-to-tail analysis.

Functions from Messy Implications

Finally we also know that implication might be extended to messy practical logics like 3-values logics with inputs that are neither strictly true nor strictly false. When we convert these into functions we generally accept that there may be errors. Some inputs might look like they should work but when run they fail. This is handled in a number of way in programs but most often the result is to produce a “side effect”, an aspect of the program that goes in a different direction than what normal behavior should do. You might find this done through what are known as Exceptions.

Stream json2csv(Stream s) throws IllegalArgumentException { ... }

There are many more ways the a program might produce a side-effect that captures the spirit of messy implications. Many are never declared and are instead “implicit”. For example, if your computer runs out of memory the function might end without any error given by your program because the error is so crucial to the entire computer that the system itself interrupts all programs and takes control away from everyone to sort out the failure. The best models for this situation tend to be in “Modal Logic” where we speak the “necessity” or “possibility” of outcomes. We will return to this in future units on Modal logic and Default Logic.
