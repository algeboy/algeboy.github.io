33  Default Logic

Let’s dig in to the logic of defaults. The setting we want to consider is when we make our reasonable assumptions about expected deductions but acknowledge that some of our assumptions could be overridden if new information is brought to light. The point is to outline in a disciplined way the process of modifying our assumptions. The method we will outline does to work in all situations however. We will limit our exploration to scenarios that meet the following criteria:

  • We have a clear authority to decide on rules. This might be a design specification, a client, or requirements of governance & laws.
  • We can spend the time/resources to explore the optimal configurations. Often setting up a default logic plan takes some upfront work.
  • The complexity of the solution does not interfere with desired implementation. You can think of the opposite: suppose the instructions are so complicated that you spend more time using the new instructions than getting actual work done.

Now if your situation meets these criteria then the following tool is for you!

33.1 Defeasible Logic & Default Reasoning

Defeasible Logics are non-monotonic logics where we explicitly signal what judgments can be made invalid by later evidence, rather than assuming that all judgments would collapse under later judgments.

Example. Each of the following is valid in a manner that does not become invalid by the addition of future evidence.

  • If my battery is dead then I cannot make a call.

  • If \(0<x<1\) then \(x\leq \sqrt{x}\)

  • x = "Dog" and y="Man" then x+y=="DogMan"

33.2 Defeasible judgement

A judgement \(A\vdash B\) is called defeasible, denoted \(A\overset{D}{\vdash} B\) if the addition of some judgements \(C\) may lead to invalidating it \(C,A\nvdash B\). We can capture this as a modal condition

\[ A\overset{D}{\vdash} B \qquad \equiv\qquad (A\vdash B)\wedge \big(\diamond \big( \exists C. (C,A\nvdash B)\big)\big) \]

Do not worry about the symbols if they don’t help you. You can break it down by saying

  • You much have A leading to B, and
  • It is possible to add further evidence C where C together with A no longer leads to B.

The propositions “C” that occur in a defeasible judgement are called defeaters. Identifying defeaters is a mix of common sense and subject matter expertise.

A common sense defeater

  • You click on the image file leading to it being displayed in the browser.

  • A=“You click on the image file”

  • B=“It is displayed in the browser”

  • Together \(A\vdash B\)

  • It is possible that the image type is not supported by the browser.

  • C=“Image type is not supported”. (A defeater)

  • Together \(A,C\nvdash B\)

Therefore \(A\vdash B\) and \(\diamond (\exists C)(A,C\nvdash b\). So \(A\overset{D}{\vdash} B\) is a defeasible proposition..

In this example it is likely that common sense convinces you that “C=Image not supported” would defeat the rules. But in the following example it would only be someone with specific knowledge that could inform us about the defeaters.

A expert dependent defeater

Consider the following three

  • A = The container is bowl shaped.
  • B = The container holds liquids.
  • C = The liquid is helium.

Our common sense will tell use that \(A\vdash B\), e.g. water is help in a bowl, oil is held in a bowl, and so one. This is a sound judgement. However, an expert in low-temperature superfluids would be able to inform us that liquid helium exhibit zero-viscosity and therefore has no friction the side of the bowl and will creep up the sides and pour over the edges. This defeats the claim and so \(A\overset{D}{\vdash}B\). Of course this could only be expressed to us through a subject matter expert as our daily experiences do not encounter liquid helium.

Alfred Leitner, 1963, Public Domain.

Was the first entailment just wrong?

When we first deal with default logic from the lens of deductive reasoning it is tempting to want to revisit the initial entailment \(A\vdash B\) and claim this was in error. There are at least two responses to give to this feeling. First of all, humans built logic and did so in the hopes of solving their problems. So if default logic makes for easier reasoning on some problems we should not be shy to use it even if it is not the right tool for some other applications. The second response is that if we think long enough there is very little outside of formal mathematics which would ever deserve the judgement \(A\vdash B\) because nearly every claim we will make will be couched in some default assumptions often unspoken and too difficult to uncover. So in a practical sense we would get nothing done if we insisted on beginning without defaults. Thus if we are making a specification of a program and want to explain a feature as

“You click on the image leading to the image displaying in the browser”

We are not behaving irrationally. We are merely lacking the later specificity that will unpack this discussion. And it gives us a compact digestible goal to begin aiming at.

And in case you think this is a choice only faced by practical sciences just take a look at the question of solving \(x^2-2=0\). I natural default is to assume that \(x=\pm \sqrt{2}\) is two solutions. That is until you meet a subject matter expert who wants numbers to represent binary values modulo 2. Defaults are natural, embrace them and your reasoning will be easier on others.

33.3 * Select All

\(A\overset{D}{\vdash} B\)

  • A is valid
  • B is valid
  • A leads to B
  • Some condition C can defeat A leading to B
  • Possibly a condition C that defeats A leading B
  • B is both valid and invalid

33.4 * Select All

You are designing a specification for a print option of your document. You have

  • A = “Select Print Document”
  • B= “A paper copy will come out of the printer”.

Your design is that \(A\overset{D}{\vdash}B\). Select some proposition that would be reasonable to include as “defeaters” to this claim. Keep in mind the original three criteria for default logic.

  • Paper jam
  • No toner
  • No paper
  • There are other print jobs
  • There are voltage drop in the power socket.
  • There is a denial of service attack to your network.

33.5 Priority Orders

Default Reasoning in a defeasible logic attaches a priority order \(<\) (for our purposes assumed always to be transitive) to the defeasible rules. The process of judgement is that high priorities can defeat lower priorities to draw conclusions. There are still many parameters to select: e.g. a breadth-first, vs. depth-first override of priorities. These get into the specific algorithms which can be applied and we will consider those to be technical details beyond the scope. We assume we are given the priority order and its reading order and proceed deductively form there.

Example.(This is a classic and so while not about computing it is worth teaching for the cultural significance).

  • Tweet is a bird; therefore, Tweet can fly.
  • But it turns out Tweet is also a Emu, so Tweet can’t fly.
  • That is unless Tweet is in a crate to ship to the zoo, then Tweet really can fly.

This demonstrates how defeasible reasoning based on a “common sense” priority order, meaning we know by common sense that

  1. Bird \(\overset{D}{\vdash}\) fly. (Defeasible but still logical claim)
  2. Emu \(\overset{D}{\vdash}\) \(\neg\)Fly. (defeats rule 1) so Crated, Bird \(\overset{D}{\vdash}\)Fly \(2<3\)

Example

  1. If Admin users can delete users.
  2. No user can delete themselves.

Here \(1<2\) meaning that while the admin can delete people, that rule is defeated when it comes to deleting them self.

ExampleConsider the following business logic for customer discounts. Now we provide a priority order

LetDisc(x, p%)mean customerxgetsp%off.

  1. Loyal customer:Loyal(x) ⟹ Disc(x, 10%)
  2. Tuesday Special:Tuesday() ⟹ Disc(x, 20%)
  3. Student default:Student(x) ⟹ Disc(x, 20%)
  4. Clearance-item:ClearanceItem() ⟹ Disc(x, 50%)
  5. Fraud-flag exception:FraudFlag(x) ⟹ Disc(x, 0%)

  • A loyal customer comes on a Tuesday but can’t find their loyalty card and the clerk doesn’t recognize them. What discount should they get?

One of the strengths of a priority order is that if we build our defeasible logic around such an order we can treat the priority order as furhter data, thus dynamically responding to changing priority.

  1. Show In-house Login.
  2. Show Google Login.
  3. Show Apple Login.

Priority Cases
