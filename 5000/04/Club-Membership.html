22  Subsets and Partitions

Our progress this far

  1. Identify context, implicit and explicit (import, include, using, etc.) and the logic that requires (e.g. Constructive, Classical, Paraconsistent, Modal, Linear, etc.).
  2. Develop logical operators to capture forms of reasoning we agree to consider valid in that context, e.g. AND (), OR (), IMPLIES (), NOT (), FOR ALL (), THERE EXISTS (), NECESSARY () and POSSIBLY () are common.
  3. Wrap these with data types so that we can narrow our logical context to avoid contradictions.

Final Objective: Combining data types

Our final objective is to combine the data types we just made into more complex structures similar to how we combine logical operators to make complex reasoning. Don’t be alarmed by the term “complex” here. We mean it in the spirit of a building “complex” as one made from smaller parts and not in the colloquial sense of “complicated”. It is nevertheless true that the more parts a system has the more we have to be mindful about the resulting meaning. So it is unavoidable that some data types do become complicated.

* Objectives

  1. Define Injective, Surjective, Bijective

  2. Characterize injective, surjective, bijective by equivalent properties

  3. Syntactic properties of right/left/two-sided invertiblity

  4. Semantic properties of the commutative-diagram left/right cancellation properties.

  5. Identify subsets / Filtered data types as injections,

  6. Identify partitions / data types with overridden equality as surjections

  7. Develop intersections / pullbacks to combine data on what is common

  8. Develop unions / push-outs to unify data with overlaps.

  9. Develop further diagram skill with Venn diagrams and Hasse diagrams

We now have several logics in front of us and are on our way to turning this into software. One lesson we are learning is to keep concepts simple and build up complexity from small steps we can trust. So now comes the problem of mixing two context. In our first video we will encounter a new problem this brings. A paradox that forces us to add to our logic. The result is what today is known as “Higher Order Logic”, which include several sublogics with names like “Set Theory”, “Type Theory”, “Classes”, “Kinds” and “Sorts”. These are all different attempts to avoid mistakes but remain flexible.

* Objectives

  1. Identify the limits of first order logic, e.g. that you cannot combine facts from two contexts without contradictions.
  2. Be able to read set theory notation
  3. Use set theory notation to repair problems in first order logic.

We need higher order logic when…

The same sentence, evidence, or data can be judged differently in two contexts that need to be used together.

* Quick Check

Your project uses 2D and 3D points. Will you need a higher order logic? - Yes *

Correct: The arithmetic storage and display of 2D points is different from 3D points and you cannot blend the two without errors. So your will need some higher order logic to separate the context. For example you might create two different types of data. - No *

Think about the point (2,1) and (1,0,1). Is there really any way that you could use these interchangeably without causing some errors?

22.1 Annotation

Perhaps the simplest and most common solution to higher-order logic problems is to annotate the data. Annotations are a general term for all the symbols, superscript, subscripts, highlights, colors, etc. that we might add to text to indicate there is something special going on. Here are three of the most common forms of annotations.

  • (xX) Here (x) is the data and (X) the annotation. The symbol () read as “in” is meant to read as if the data (x) is in the context of (X). This is especially common in mathematics circles where might write (5) to say “5 is in the real numbers” (real numbers are just decimal numbers).
  • x:X or X x. Here x is the data and X the annotation. The symbol : read as “has type” is meant to read as if the data x is in the context of the data type X. This is especially common in programming circles where might write Float x or x:Float to read as “x is a floating point number.

* Quick Check

You read the following code. Are you likely to be using higher-order logic?

def convert(file, format):
s = read(file)
return save(s,format)
  • Yes

Unlikely. While the names of the function and the variables give us clues that the data have special roles, there is nothing in the code that annotates this for the program and so we should assume we are operating under the conditions that any data could be coming in or out of this function.
