Day 1: Should you Modify your Priors or Your Reasoning

When you make a mistake you typically have one of two reactions:

  • Find out what you did wrong.
  • Figure out what you will do next.

These two strategies of often intermingled but they point to two largely distinct strategies for problem solving.

Default Reasoning.**

If you can understand what went wrong you might be able to fix it by introducing a modification to your original reasoning. You in effect had default assumption that turned out to be defeated by later evidence. By going back to that default you reset you prior understanding and move forward with a new default position.

In computation this might be something like assuming that the data set you loaded had been sorted alphabetically because all other examples had been sorted. But then you run across one data set that is not sorted. It defeats your default hypothesis. You then go back to your instructions for handling the data and look for what instructions should be made for unsorted data. Perhaps you first sort it, or perhaps you are instructed to removed it form the study. The point is, you located the source of the error and can now behave rationally form there.

Adaptive Reasoning.**

Meanwhile in the “figure out what to do next” camp, it may not be important to know how you go where you are, but you sure need a plan to get through the error. Imagine you’re running an app on your phone and it suddenly freezes. You may have no idea what strange combination of events occurred to make it freeze. It might be impossible to retrace your steps precisely enough to ever reproduce the bug. But it’s typically not that important to solve the source of the puzzle because you might just close the app and restart it to find it now works. It is a messy alternative to problem solving because we might loose some work we already did but it is far less time to reenter some values than it would be to do a detailed study of what triggered the bug.

This is a situation that calls for “Adaptive Logic”. Loosely speaking we run two logics. A lower logic that has a set of very realistic properties such as assumptions that data can be contradictory, resources limited, power to code go out etc. This lower logic is pessimistic and difficult to use for most natural projects so then we install an Upper Logic with convenient properties like “programs never freeze” “you have all the resources you need” and so on. The lower logic runs the Upper Logic almost like a video game runs on a computer or an webpage runs in a browser. It is simulating an environment that is well behaved. But should a problem actually occur, the lower logic is there to step in, close the app, reset, and start over.

Inconsistent reasoning and how to make it consistent

Before doing a deeper dive into the precise mechanics of default and adaptive logic it will help us to consider first how it is that we represent mistakes, bugs, and other inconsistent events in logic. That will make it much more obvious what are the strategies to begin fixing them. Chief amongst the strategies is to realize that mistakes/bugs/inconsistences are always a matter of perspective. They do of course actually happen. Which proves they are in fact “logical”. They only appear “illogical” because we lack the right context when we first an approach the question. So lets revisit context as means to identify inconsistency in a logically sound manner.

Classical Inconsistency

In classical logic, the type of logic we often us in theory, we want avoid a situation where everything is true. This may seem a strange way to define inconsistency but imagine if everything is true then what would be the point of any reasoning? One way we can state this is by insisting on at least one false assumption.

Non-monotone logic

Lets revisit validity to see a nuance that we never settled but which probably was filled in with a default assumption which now we need to correct.

Recall that we write (AB) we are saying that (A)leads to, validates,(B)

Example.If I see the symbol 📶 then I can browse the web on my phone.

  • A = “I see the symbol 📶”
  • B = “browse the web on my phone”
  • (A)

However we have all of us experienced a situation where the icons are misleading and although we have a signal we somehow cannot get through. So here is an expanded scenario.

Ex.If I see the symbol 📶 then I can browse the web on my phone.But often when I land after a flight in a new time zone my phone can’t locate my carrier so it doesn’t work to browse after all.

  • A = “I see the symbol 📶”
  • B = “browse the web on my phone”
  • (AB)
  • C = “New time zone”
  • (C,A B)

This is a demonstration that logical reasoning is quite oftennon-monotonic

DefinitionA system of logic ismonotoneif whenever (AB) then (C,AB). If this is not always the case then we call the logicnon-monotonic.

Whether a logic is monotone or non-monotone has all the usual divisions of being a mix of Theoretical, Computational, and Practical. It is not about contradictions or the meaning of truth vs. evidence. It is about whether we insist that validity always builds up (monotone) or if validity can be “defeated” by future evidence. In the phone example it was logical to read (AB) in fact this is what the design of the phone says is the point of the icon. But it is also logical to defeat that logic when further evidence gives a broader context that explains exceptions to that behavior.

The point of non-monotonic logic is to offer scaffolding to work through scenarios where non-monotonic reasoning is required and select the desired behavior. Often these situations are left unresolved or left to individual programers to select a solution based on whim or instinct rather than optimal behavior.

The world of default and adaptive logic are filled with algorithms and strategies that optimize against desired cost functions (e.g. make the most people happy). A main objective to make students aware that there is an entire body of algorithms and known limits to exception handling and often the ad hoc solutions are suboptimal.
