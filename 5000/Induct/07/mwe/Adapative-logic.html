Using Adaptive Logic

The point of an adaptive logic for computation is to put a formal system of reasoning around various situations in computing that may fail in unpredictable ways, but are also somewhat common occurrences. The loose plan is to create two logics, one stronger than the other. The weaker logic represents the actual computation, and the stronger logic is like a virtual machine running within our systems with its ideal rules. When the ideal rules break, the weaker logic takes over.

Overview

Signs of an Adaptive Logic Scenario

  1. Opaque causes of error.
  2. Clear restart option(s).
  3. Rules of ideal world have a weaker realistic version.

What we don’t plan to model adaptively

There two extremes we don’t care to consider.

  • When there is a bug. If you failed to call close on a file at the end of your program it caused files to get corrupted, you really should fix your code, instead of fussing the rules of logic to explain it away.
  • When event are outside our control. How a computer behaves when you spill hot coffee on the keyboard is a step too far in most program designs.

Adaptive logic is good for Abnormalities

In a word addressable “Abnormalities”.

  • Your program works fine in your environment but not when run on other computers.
  • You can’t reproduce the events reliably.
  • There are multiple ways to reach the problem and they all point to different causes.

A Scenario of Abnormalities

Let’s look into one scenario where we model the behavior of closing an application.

Designed behavior

First lets look at the design goal. You have an application where users can create some data. You have the following design goal:When a user closes the app with unsaved work, the app should put up a warning telling them to go back and save the work, or delete it and continue closing. In symbols:

  • (U) = “There exists unsaved work”
  • (C) = “Close application”; hence, (C) = “Do not close application”.
  • (D) = “Delete unsaved work.”

The rule given is that necessarily (U) and possibly (C) leads to ((C)) or (D). More precisely((U)( C) (C)D)

Technical Remark. We are using qualifiers “necessary” () and “possibly” () to clarify the subtle point that closing is a process over time. If we strip these away and write(UC (C)D)it would read as saying that (C) is true, i.e. (UC C) is one of the elimination rules of an AND. So that would seem to immediately remove even the option not to close, which we actually want our user to have. By using “possibly C” ((C)), we are chasing down the scenario where it is possible to have (C) or (C). Given that we put in qualifiers it makes sense also to require that there actually be unsaved work before warning the user about loosing it; hence, (U).In reality the better qualifiers are from temporal modal logic that are better suited at describing knowledge over time. As we are not studying such logics we leave this as a hint that if you continue in this direction there are many resources to help.

Race / Deadlock Scenario

  • Event A global resource warning prompts you to shut apps down. In haste, you attempt to close an app with unsaved work. You see the warning dialog and click Abort (intending (C)). Meanwhile, the system begins shutting apps down automatically (forcing (C)).
  • Result The system enters a confused state where both (C) and (C) are active (e.g., competing threads: one closing, one restoring).

Formally, we have:(C(C))Now, classically, this shouldn’t be possible, and it is not in our classical theoretical logic. But reality trumps theory. From the perspective of the program we are best able to explain the current situation as a logic that allows such contradictions. (Perhaps a 3 valued logic like a paraconsistent logic).

Modeling the Problem

Having a logic that allows for inconsistency does not mean to give up on reasoning, rather it allows us to embrace fixes and clarifications that don’t seek to diagnose the inscrutable circumstances that got us here but rather focus on what to do next. Let us write down precise differences in our classical expectation and what it is we actually witnessed.

Upper Logic

Classical logic would push toward resolution via Disjunctive Syllogism (()):(())implying the system should delete the unsaved work and proceed to close. Let’s call this the Upper Logic UL, which is the logic we think should be there.

Lower Logic

But in reality, the system hung due to a race/deadlock (two threads enforcing (C) and (C)). The contradiction persists instead of resolving. At a lower level we have a logic where () is not validated. Instead we have much more boring derivation that requires no special rules at all.(())We call this a fact because you can prove this any logic that Ands (()), Ors (()), and Nots (()). All we are saying is that EITHER we delete the unsaved work and continue, or else we are in a confused state of ((C C)). Let’s call this the Lower Logic LL, which is the logic we actually have.

Abnormalities

We can treat (C(C)) as an abnormality (Ab()) triggered by data () (e.g. running out of memory and entering an emergency shutdown). Now we can return to the classical rule and describe it as n Conditional Rule (CR) meaning it depends on not having the abnormality (Ab()).(C,  (C)D {CL} D C,  (C)D {CL} D Ab())We would say simply that (C, (C)D _{CL} D) is “Conditional Rule”, conditioned on the data (). As long as we avoid the abnormality (Ab()) we have the intended behavior. Rules in the lower logic LL are by design always Unconditional Rules (UR).

Summary of the Model

What have we achieved? We have managed to create an underpinning of logic where the behavior we are witnessing is not illogical. It is merely what this logic allows. And because of this we can now design a logical step to follow this. Ideally we fix the “problem” – i.e. the case (C(C)) which doesn’t fit our intended classical expectation.

Fixing the problem

Having a lower logic that accurately separate the abnormal behavior, if they occur we no exactly problem to try to address. Unlike default logic, where one rule overrides another in cases of confusion, we do not need to know precisely how created the abnormality. We simply observe that it occurred and proceed with a logic to handle that scenario. For example, it might be that in a confused state the data the user has is also corrupted and could cause harm to our system if not removed. We might therefore proceed with a rule that deletes all user data hasn’t been saved. (E.g. removing all temporary files.).((CC)D())Or perhaps we know this application space is safe and we have other means to protect against errors so even a partially save project might be reconstructed from temporary files when the application is restarted. So we might purposefully save all temporary files overriding any user decisions.((CC)D())Whatever the design choices, we now have a system of logic to express logical outcomes in the face of inconsistent data.

The catch

The one obstacle is that if we proceed with conditional rules only to find conclusions that are eventually abnormal, then we leave behind inconclusive logic. So what we maintain is a rule that as prove our steps we leave a mark next to any claim which is later invalidated by an abnormality. This means that ever step in our proof maintains an ongoing list of possible abnormalities. If any should occur we search back wards and invalid (mark) all rules that are conditioned on that abnormality. Those no longer count towards the reasoning leaving behind a completely logic progression of step, if only in retrospect. The precise mechanics of back tracking could seem to take a long time to search. But there is a weapon in the programmer’s arsenal called “dynamic programming” (or memorization) which in effects reuses previously made calculations and behaves much more efficiently. You can study those details in a future algorithms class. For now, we simply apply in our specific examples.

Revisiting the Scenario

Let us imagine that we take the pessimistic solution. We are running several apps at once when our computer tells us it is dangerously low on memory and recommends we close applications. We panic and start closing application, one of them having unsaved work which triggers the warning. We click to abort the close so we can save the file, but by this point the operating system is in emergency mode and sending mandatory close calls to all apps. We enter an abnormality of (CC). This violates Conditional Rule and drops our app out of the hypothetical classical logic into the real world with inconsistencies. Then locating the pessimistic rule, we delete all the user data. Miraculously it was actually one of our temporary files that was growing in size and causing the problem in the first place. Having just deleted it, the system recovers and goes back to functioning normally. Crisis averted, some user data lost.

Adaptive Logic Tables

Let us work out the formal adaptive logic table for this scenario using the following propositions: Defined Propositions:

  • (U) = “There exists unsaved work”
  • (C) = “Close application”
  • (D) = “Delete unsaved work”

Additional Propositions:

  • (M) = “Memory warning issued by system”
  • (E) = “Emergency system shutdown initiated”
  • (Ab()) = “Abnormality: ((C C))” where () represents the race condition data

Rules:

  • CR1 (Conditional): (U C (C D)) [Standard close behavior - conditional on no abnormality] Abnromality (Ab()=C(C)) when () is some complex race condition.
  • (Unconditional): (M E C) [Emergency close - always applies]
  • (Unconditional): (U C ((C C) D)) [Lower logic reality]
  • (Pessimistic Rule): ((C C) D) [Abnormality resolution]

Adaptive Backtracking.

  • Step 6 is made by CR1, but initially conditional on the absence of the abnormality (Ab()).
  • Step 7 triggers the abnormality (Ab()) which marks 6 and removes it from further consideration.
  • The valid logical thus now skips 6 and goes (1).
  • So in the end, the pessimistic rule takes over and deletes the file.

This table demonstrates how adaptive logic handles the contradiction by:

  1. Detecting abnormalities when classical logic fails
  2. Marking invalid steps that depended on violated conditions
  3. Applying specialized rules (PR) to resolve abnormal states
  4. Maintaining logical consistency through retrospective validation
