Lists, Trees, & their Algebra

When we reason inductively we look at evidence we have, conjecture about possible options, and compile a strategy that works through the cases we identify. When our concerns are computational we need all our evidence to come in the form of data, data of various types. And the strategy is to develop transformations of our data. That means functions of a special shape we call operators. All the operators together form the so-called “algebra” of our induction. Many times the operators will be used over and over again, in what we call “recursion”, reflecting the idea that sometimes complexity comes from repeating simpler ideas over and over again. Think of \(4n\); that is simply \(n+(n+(n+n)))\) so it is addition repeated 3 times. Let’s begin with an archetype situation where we need induction.

Once we create data inductively we will need a strategy to take such complex data apart, and for that we reverse the constructions in a process known sometimes as “coalgebra”. Instead of operators we reverse the direction and have “cooperators” and instead of recursion we make streams of “corecursion”. But all this is too abstract to take in without some examples. Coalgebras will come next lesson!

Defining the operators of the List algebra

Let us write List[A] to mean the type of data which we regard as a list of terms of type A. For example, List[Int] is a list of integers, List[String] is a list of String objects, List[List[Int]] is a list of lists of integers, and so on. To make a list we have basically 2 options

  • Make an empty list, traditionally called “nil” nil:List[A] also denoted []:List[A].
  • For every constant a:A, there is a unique operator that pre-pends a to the list. Traditional notations include cons(a): List[A]-> List[A] or a more operator looking notation like a::_.

Technical point: sometimes it is convenient to treat all empty lists as equal, but the way we have done it so far []:List[Int], []:List[String] would make two empty lists, one for integers, one for strings. In some programming languages you can unify these types by creating a single empty list of type List[Any] . The idea is that when the time comes to decide, any type of entries will work. After all a list with nothing in it doesn’t need to have a specific type. That model doesn’t quit match the algebra so we leave that technical choice to the side, but you might want to try it on your own.

Example of List Building by induction

An integer would be the letter “i” and so the plural, a list of integers, becomes “is” (“eyes” not “iz”), which in our notation could be is:List[Int] = 5::[4::[1::[]]]. The brackets serve as parenthesis and most programming languages will let you remove them, e.g. 5 :: 4 :: 1 :: []. In fact programming languages offer lots of syntax alternatives called “syntactic sugar” such as [5,4,1]. In this situation there is one nil operator but also one operator for every integer! So if integers are 32-bits, that means \(2^{32}\approx 4\times 10^9\) cons operators!

Operators as Formation and Introduction rules

What makes this induction is the use of operators to build up the data. Operators can come be many, e.g. one nil operator, and as many a::_operators as there are terms a:A. On a formal level we think of the application of operators as “introduction rules” (constructors/setters). Let us look at the sequent version of these rules.

  • Formation \(\frac{\Gamma\vdash A:\text{Type}}{\Gamma \vdash \text{List[A]}}\)
  • Introduction(Nil case): \(\Gamma \vdash []:\text{List[A]}\)
  • Introduction(Cons(a) case): \(\frac{\Gamma\vdash a:A, tail:\text{List[A]}}{\Gamma\vdash (a::tail) : \text{List[A]}}\)

Using the algebra: Elimination and computation rules

The elimination rules and the associated computation rules are so prescribed for these data types that they are often not even explained. These are so common they even have their own special names: “Principle of Induction” and “recursion” respectively. Here they are as sequence for Lists.

  • Elimination(“Principle of Induction”): $ { extract(as) : ( ) } $.
  • Computation(“Recursion”): \(\Gamma \vdash extract([]) := Left()\) because you can extract nothing from an empty list. Otherwise $ { extract(head :: tail) := Right( head, tail) } $

Don’t get too strict about these names. Many authors use them in slightly different ways.

A sample use

> as:List[String] = ["dog", "cat", "mongoose"]

def length_of_list(as:List[A]): Int =
    as match {
        case [] => 0
        case head :: tail => 1 + length_of_list( tail )
    }

> length_of_list(as)
3

Ways to think about many name operators

Arguably we might prefer to think of constructing lists as taking as input both a head a:A and tail tail:List[A]. But that leads to a very complicated algebra and so it is easier for us to reason about the parts that are the same, the List[A]. You might find it helpful to think of similar situations you might encounter already.

Think of this as an operation similar to say the an exponent, e.g. \(x^2\) or \(x^3\). You can imagine a calculator button for each operation, and you can imagine a bigger calculator, like a computer, could make one for larger powers in fact one for every integer. Having multiple operators with similar names is normal in your everyday computation.

So what do we have in total?

An “algebraic structure”, or simply “an algebra” refers to any set, or type of data, \(A\) equipped with operators \(\omega:\Omega\)

\(\omega:A^{|\omega|}\to A\)

Here \(|\omega|\) means the number of inputs to the operator, e.g. 2 for binary, 1 for unary. This called the valence (or arity) of the operator. Remember that \(A^n\) means lists of n terms form \(A\), e.g.

  • \(A^2=\{(a_1,a_2)\mid a_1, a_2:A\}\)
  • \(A^1=\{(a_1)\mid a_1:A\}\)
  • \(A^3=\{(a_1,a_2,a_3)\mid a_1, a_2,a_3:A\}\)
  • \(A^0=\{()\}\), that is right, the list with nothing in it is still one thing, so \(A^0\) has one term, just like \(10^0=1\) and \(x^0=1\).

For example, the decimal numbers \(\mathbb{R}\) have many operators including addition, multiplication, negatives, zero, and one. So \(\Omega=\{+,\times, -, 0, 1\}\) and the functions are

  • \(+:\mathbb{R}^2\to\mathbb{R}\) because we add 2 numbers.
  • \(+:\mathbb{R}^2\to\mathbb{R}\) because we multiply 2 numbers.
  • \(-:\mathbb{R}^1\to\mathbb{R}\) because we negate 1 number. Warning: it is possible to subtract numbers as well but technically that would be a different operator because it would 2 numbers to subtract. Let us keep things easy and just use negatives.
  • Zero is a constant, which in other words means a function that depend on no inputs, we write it \(0:\mathbb{R}^0\to \mathbb{R}\). Remember \(\mathbb{R}^0=\{()\}\) has only one term, and so the function \(0\) sends that one term, the empty list \(()\) to the correct constant \(0.000000....\). In programs we might write def zero() : Reals = 0.000, notice the () is the single input to this function.
  • One is another constant we write it \(1:\mathbb{R}^0\to \mathbb{R}\), it too needs no inputs. Again the empty list () is sent to 1.0000, i.e. def one() : Reals = 1.00000.

A tree algebra

Having made the case that recursion uses algebra, we can think of a binary tree as having two operator: root & branch.

sealed trait Tree[A:Type]
case Root(a:A) extends Tree[A]
case Branch(left:Tree[A], right:Tree[A]) extends Tree[A]
typedef struct Tree {
    enum { ROOT, BRANCH } tag;
    union {
        struct { A value; } root;
        struct { struct Tree* left; struct Tree* right; } branch;
    } data;
} Tree;
type 'a tree =
    | Root of 'a
    | Branch of 'a tree * 'a tree
data Tree (A:Type) : Type where
  root : A -> Tree A
  branch : Tree A -> Tree A -> Tree A

In traditional Java and similar versions of C++ you could create the effect of trees using hierarchy of classes. Here is a simple example of a binary tree with a root operator and a branch operator.

public abstract class Tree<A> {
    public static class Root<A> extends Tree<A> {
        public final A value;
        public Root(A value) { this.value = value; }
    }
    public static class Branch<A> extends Tree<A> {
        public final Tree<A> left;
        public final Tree<A> right;
        public Branch(Tree<A> left, Tree<A> right) {
            this.left = left;
            this.right = right;
        }
    }
}

Java latter added record which allows for such constructions in a shorter syntax.

public sealed interface Tree<A> permits Root, Branch {
    public record Root<A>(A value) implements Tree<A> {}
    public record Branch<A>(Tree<A> left, Tree<A> right) implements Tree<A> {}
}

In math notation we tend to abbreviate the operators as \(\rho_a\) for the “root operator” and \(\beta\) for the “branch operator”, and \(T(A)\) for the set of binary trees with nodes labeled from elements in \(A\). This makes the form of the operations much more obvious because we have removed distractions such as the meaning of the word “tree”. \[ \rho_a:T(A)^0\to T(A)\qquad \beta: T(A)^2\to T(A) \]

WarningCircular math definitions

Notice the math description of the tree algebra is at best incomplete and at worst circular. Unlike the computational definitions given above, here we appeal to \(T(A)\) as existing already with all binary trees labeled form \(A\). We then have to somewhere else sit down to explain what all that means. Often in math we simply do not do this. We give instead verbal descriptions and some examples. For instance the natural numbers are often described as \[ \mathbb{N} = \{0,1,2,3,4,5,\ldots\} \] While childhood is a good place to learn, it not known for its precise meaning. So leaving the reader to imagine \(\dots\) for themselves as the right pattern for counting is dangerous choice. Likewise asking our readers to imagine the precise nature of binary trees or formulas is problematic.

In truth, to properly define concepts in mathematics often implicitly depends on computational definitions which are later wrapped in math notation and vocabulary to disguise is computational origin.
