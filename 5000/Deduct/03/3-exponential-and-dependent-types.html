(30 mins) Dual logic and Programs

Math156 Dual logic and Programs

Is a good idea is worth repeating? Well in math and logic once we have solved a problem we don’t really need to solve it again. Rather what we mean in this situation is that we can repeat the spirit of the idea but with some useful changes. The variation we want to explore here are when the roles of the arrows are all reversed behavior can occur in reverse as well. Think of this as swapping inputs with outputs, saving a file verses reading a file, opening a window verses closing a window, and so on. When we do that we are in effect swapping the elimination rules with the introduction rules of some data types. With logic that means for example to swap AND with OR, True with False, and many similar so-called dualities. It is often a strong way to get a new functionality without much new work. But sometimes these dualities actually uncover missing parts of the original problem which help us make a better understanding of the entire logic.

* Objectives

  1. Dualize the logic and diagrams associated to it.
  2. Create the semantics for AND as dual to OR
  3. Recognize the diagrams of for all () and for some () as dual.
  4. Identify ({a:A} B(a)) and ({a:A}B(a)) data types as wrapping quantifiers.

Data types for quantifiers

Now that we approach mastering the logic of AND, OR, IMPLIES, and NOT we have missing only the QUANTIFIERS (, ) (qualifiers (,) will occur later). We already saw that to make “for all” was really just a repeated use of “AND”. So it may come as little surprise to discover that the data types for all are repeated use of pairs, sometimes called “tuples” but they can include such things as structures and arrays as well. These data types have become known as “dependent types”. We will work through the “Dependent Pair” type here and in exercises you will explore “Dependent Functions”.

Co-Universal Program Design

  1. Design a pattern of flow to your new data types from the given data (introduction rules rules “constructors/setters”)
  2. Repeat that same pattern of flow with a competitor solution.
  3. Verify that your type of data can be exported to your competitors solution uniquely (elimination rules). Think of this as migrating your solution to their solution. The uniqueness here means you don’t have to get caught up in future choices of how to convert. Doing so means you program is now brittle and will depend on configurations and is, well, not co-universal.

Notations

Dependent pairs have several notations.

  • In mathematics (_{i:I} X(i)) is known as a “disjoint union” with terms denoted (x_i).
  • In logic (_{i:I} X(i)) which reads as “for some (i), a term of (X(i))”. This is a pun on the work “sum” and “some” which only works in English.
  • In programming X(1)+X(2) adding more terms as need is a sum of types but dependent pairs take on notation as diverse as <i,x>, i**x, but I believe in time it will converge the math notation (x_i). The only problem is that the LaTeX way to use subscripts is x_i which now clashes with the snake-case style of program names. This is easy to fix but as of today it is not yet settled.
