Equations from Diagrams

We often benefit from thinking with pictures. One reason this can be better than words on their own is that we can often use a picture two show a complex set of conditions with few actual symbols. The complication however is that pictures are often one example and not a general claim as we might be hoping to argue. For this reason it is important to clarify our language of pictures and to be precise enough that others can read this without confusion. Having now built up (1) Types of data, (2) Functions between types (3) Composition of types, we are now in a position to draw pictures that put these constructions together. The key tool is what we call a “Commutative Diagram”

Objectives

  1. Identify a commutative diagram
  2. Convert commutative diagrams into equations
  3. Convert equations of functions into commutative diagrams.
  4. Use the Story-board style to communicate the evolution of a commutative diagram.

Reviewing Composition

Let’s take apart the story into two major lessons. The first of these is the concept of a “commutative diagram”. The idea here is known two most of us as the way we read a flow chart. We have nodes with a rows and if we follow a path of arrows then we are following the cumulative effect of applying one transformation after another. If we start to think of this in the logic we are building we can think of the arrows as implication, or if they concern data we call them functions instead of implications. The nodes then become data types.

  • Nodes: Data types
  • Arrows: Functions between data types
  • Composition: passing data through multiple functions.

You may be familiar with composition of functions and its properties, here is a refresher. The takeaways are that

  • Definition ((gf)(x)=g(f(x)))
  • Associativity ((h(gf))=(hg)f))
  • But non-commutative ((gf)) does not in general equal ((fg)).

Notice above all that we are looking at equations. Equations are parts of mathematics we can test and use to constrain questions and crucially to solve for unknowns. It is a form of “Algebra”. If we bring equations into the design of programs we will find the algebra confines us a bit towards solving the questions in the right way. If we break an equation we have a bug. So we can make tests that try different values of input in the equation and see if they hold. If not we look for a bug. This equation being well inside our system of code is a local test. We do not need to wait for the eventual full strength program to find the mistakes. This is a type of debugging known as “Unit Testing”. Designing our programs to hide equations is one of the main ways we can separate off small problems that are less complex and spot mistakes early.

Software Composition

In software composition can often be written in the opposite order. For example, myFile.as_CSV().convert_JSON() is an often legal programming syntax which means to take the data myFile, apply the function as_CSV to it, then apply the function convert_JSON is applied after that. If x=myFile, f=as_CSV is and g=convert_JSON, then the logic reads as ((gf)(x)). This runs in reverse of the words we see in the program. The complication is that even in programs we can often write the order composition in multiple ways. The code below is the same composition but done more in line with the math style.

convert_JSON( as_CSV( myFile ) )

Commutative Diagrams

So now that we see that function composition is not generally “commutative”, i.e. (gffg) in most cases, whenever this does happen we should take notice. Below we see a flow chart of two events: Brushing Hair and Brushing Teeth, vs. Socks On and Shoes On.

From this model we see some events commute, others do not.

  • A commutative diagram (Brush~HairBrush~Teeth = Brush~TeethBrush~Hair)
  • A non-commutative diagram (Shoes~OnSocks~on Sock~On Shoes~On)

Over time the term “Commutative Diagram” has been relaxed to count any equation of function compositions. So while originally this was about the commutative law (gf=fg) it now includes any flowchart where two paths between the same points commute.

A diagram of functions between types is said to “commute” if any two paths between the same points give equal values.

Universal Diagrams

Now let us focus on the “Universal” nature of our diagrams. Suppose our Dad character had suggested that the child keep only one domino and one string. This would have been enough to eliminate to both a string and a domino. It is in some sense a representation of the data. Yet, the son could clearly complain that this is also to throw away a lot of the data. This would mean the “heap” strategy the kid uses is in a measurable way superior as it did not loose any information. How can the son communicate this?

With the son’s approach to a heap he can repeat everything his father’s method can so it is at least as good. In real life a software package that implements logic like this is making a guarantee that no information is being overlooked. The main idea is to

Universal Program Design

  1. Design a pattern of flow from your new data types to the given data (elimination rules “getters”)
  2. Repeat that same pattern of flow with a competitor solution.
  3. Verify that your type of data can transform the competitor’s solution into your own uniquely (introduction rule, i.e. “constructors/setters”). Think of this as migrating their solution into your own. The uniqueness here means you don’t have to get caught up in future choices of how to convert. Doing so means you program is now brittle and will depend on configurations and is, well, not universal.

Reversing the arrows: Couniversal Design

A good idea is worth repeating, but often that really means repeating with some variation. The variation we want to explore is when the roles of the arrows are all reversed behavior can occur in reverse as well. When we do that we are in effect swapping the elimination rules with the introduction rules. With logic that means for example to swap AND with OR, True with False, and many similar dualities. It is often a strong way to get a new functionality without much new work. In the exercises you will explore this duality.
